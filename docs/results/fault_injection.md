# Fault-injection experiment: how well do the pipeline's checks detect known errors?

Clean snapshot `20261001T110703Z`; 5 seeds; 11,030 injected faults in 15 corrupted snapshots. Generated by `python -m healthbridge.experiments report`.

## Method

1. Take the real pipeline's output for the clean snapshot. Rows that were loaded, selected for the default surface, unflagged and in cells without a source conflict form the **clean universe** (29,099 of 29,855 analysis rows).
2. Write a *copy* of the raw snapshot with faults injected at known positions, using a fixed seed. The copy is a valid snapshot, so the real pipeline (`load` then `build`) runs on it unchanged. Each row gets at most one fault; rows are modified in place or appended, so every fault keeps a known (file, row) identity.
3. Read what the pipeline did with each injected row: rejected with a reason, flagged, loaded unchanged (**recovered**) or loaded wrong and unflagged (**silent**).
4. A fault is *handled correctly* when the outcome is in its expected set. Rates are pooled over seeds with 95% Wilson intervals.

Three passes are run separately so faults cannot interfere: *validity* (nine fault types, 200 per type per seed), *magnitude* (one value changed by a known relative amount, 50 per level per seed, at most one per series and cell) and *schema* (file-level).

Pre-set parameters (fixed before the experiment, not tuned on it): temporal outlier = modified z-score > 3.5 and deviation > 20% of the neighbour median; source disagreement inside an evidence group > 5%; independent evidence groups conflict > 10%; dependence = at least 30 shared country-years with at least 90% within 1%.

## 3. Value corruption by magnitude

Each check is shown **on the rows it can assess**, next to the share of rows that qualify, so a check's sensitivity is not mixed up with its coverage. Either check counts as detection.

The shares of rows with a partner or enough neighbours drift a little between levels because each level was sampled from the rows left after the earlier levels (one change per series and per cell). That drift is why the per-check rates above are conditional on what each check can assess; the sampling is not balanced across levels.

Detection of **large changes (50% or more)** by the context available to the checks (the outlier check needs at least 3 neighbouring observations; the disagreement check needs another source in the same group). Small changes are left out so that context is not confounded with magnitude:

| series context only | 49 | 98.0% (89.3%-99.6%) |
| another source only | 79 | 100.0% (95.4%-100.0%) |

## 5. Precision and false alarms

*True positives* are injected faults the mechanism fired on. *False positives* are alerts on rows (or cells) from the clean universe that were not touched. *Alert rate on clean data* is how often the check fires on the unmodified snapshot, including real events; those alerts are unlabeled, so they are context, not counted as errors. Rule-based validity checks have no alert rate on clean data: a clean row passes them by definition.

| Mechanism | True positives | False positives | Precision | Alert rate on clean data |
|---|---|---|---|---|
| rejected:no_value | 1,320 | 0 | 100.0% | n/a (rule-based) |
| rejected:unparseable_value | 680 | 0 | 100.0% | n/a (rule-based) |
| rejected:out_of_range | 1,000 | 0 | 100.0% | n/a (rule-based) |
| rejected:exact_duplicate | 1,000 | 0 | 100.0% | n/a (rule-based) |
| rejected:unknown_country | 1,000 | 0 | 100.0% | n/a (rule-based) |
| rejected:invalid_year | 1,000 | 0 | 100.0% | n/a (rule-based) |
| rejected:unmapped_vocabulary | 1,000 | 0 | 100.0% | n/a (rule-based) |
| flagged:noncanonical_period | 653 | 0 | 100.0% | 0.10% |
| flagged:temporal_outlier | 998 | 83 | 92.3% | 0.85% |
| flagged:within_group_disagreement | 1,570 | 0 | 100.0% | 1.06% |
| flagged:conflict | 32 | 0 | 100.0% | 0.45% |

False positives were counted over 290,990 clean-universe row evaluations (10 pipeline runs).
92.3% of analysis rows have enough neighbouring observations for the outlier check to assess them at all; the rest rely on cross-source comparison.

**Where the outlier check's false positives come from.** They occur almost entirely in the validity pass, which changes no values. Replaying one validity pass (`scripts/diagnose_outlier_false_positives.py`, seed 1) showed that all 13 of 13 false positives had an injected row inside their neighbour window, against a chance baseline of 18.9% for untouched rows, and every one of those neighbours was a fault the pipeline rejected (blank or text value, out of range, invalid country, bad vocabulary or date). Rejecting a row removes it from its neighbours' context and can tip a previously quiet point over the threshold. So these alerts are a side effect of rejection, not errors in the clean rows, and they suggest building the check's context from the rows present before rejection. This was diagnosed for one seed only.

## 7. Summary

- Of 11,000 row-level faults, 96.6% were rejected, flagged or repaired; the rest got through silently.
- Fault types below 100% correct handling: value_change (81.5%).

## 8. Limitations and threats to validity

- Injected faults are synthetic proxies. Real errors may be subtler, correlated, or of kinds not injected here.
- Valid-looking corruptions are undetectable by design and are not counted: a country code swapped for another valid country, a sex code swapped for another valid code, or a small change to a value in a series with no context and no second source.
- Rates depend on the injection rates and magnitudes chosen, and on one snapshot. They describe this pipeline on this data, not data quality in general.
- Check parameters were fixed in advance, but they are judgements. Precision of the statistical checks depends on real events in the data being counted as alerts, not errors.
- World Bank values keep no raw text in staging, so an unparseable World Bank value is reported as missing; this is expected and is why its expected outcome differs.
- The naive loader is deliberately minimal; a careful analyst would catch more by hand.
